# KUSK Network Manager

เว็บแอพสำหรับบริหารจัดการข้อมูลอุปกรณ์เครือข่ายของโรงเรียนสาธิตแห่งมหาวิทยาลัยเกษตรศาสตร์ วิทยาเขตกำแพงแสน

## Production

- Firebase Hosting: https://kusk-network-manager.web.app

## โครงสร้างหลัก

- `public/` ไฟล์หน้าเว็บทั้งหมดที่อนุญาตให้ Firebase Hosting เผยแพร่
- `public/home.html` หน้าแรกของระบบ
- `public/login.html` หน้าเข้าสู่ระบบ
- `public/pages/` หน้าจัดการ Switch, Access Point, อุปกรณ์ และคู่มือ VPN
- `public/components/` ส่วนประกอบที่ใช้ซ้ำ เช่น sidebar และ modal
- `public/css/` ไฟล์รูปแบบหน้าจอ
- `public/js/` ไฟล์การทำงานฝั่งหน้าเว็บ
- `agent/` สคริปต์ช่วยตรวจสถานะอุปกรณ์เครือข่าย
- `firestore.rules` และ `storage.rules` กฎควบคุมสิทธิ์ข้อมูลและรูปภาพ
- `public/pages/users.html` หน้ากำหนดสิทธิ์ผู้ใช้งาน

## หมายเหตุด้านความปลอดภัย

- ห้ามเก็บ Service Account Key ไว้ในโปรเจกต์หรืออัปโหลดขึ้น GitHub
- ตั้งค่า `GOOGLE_APPLICATION_CREDENTIALS` ให้ชี้ไปยังไฟล์กุญแจที่เก็บไว้นอกโฟลเดอร์โปรเจกต์
- Firebase Hosting เผยแพร่เฉพาะโฟลเดอร์ `public/` เท่านั้น
- Firestore และ Storage ส่วนที่มีข้อมูลภายในอนุญาตเฉพาะผู้ใช้ที่เข้าสู่ระบบแล้ว
- ผู้เยี่ยมชมอ่านได้เฉพาะ `publicSwitches` ซึ่งมีเพียงยี่ห้อ รุ่น สถานะ และเวลาปรับปรุง
- ชื่ออุปกรณ์ สถานที่ รูปภาพ และข้อมูลเครือข่ายไม่อยู่ในชุดข้อมูลสาธารณะ
- ระบบไม่บันทึก Username หรือ Password ของอุปกรณ์ใน Firestore
- สิทธิ์ผู้ใช้มี 5 ระดับ: ผู้ดูแลหลัก ผู้ดูแล ผู้แก้ไข ผู้ดู และค่าเริ่มต้น
- ผู้ดูเห็นเฉพาะข้อมูลทั่วไป สถานะ สถานที่ และรูปภาพของอุปกรณ์
- IP, MAC, Serial Number และลิงก์ตั้งค่าเก็บแยกใน `switchPrivate` ซึ่งผู้ดูอ่านไม่ได้
- บัญชีค่าเริ่มต้นจะยังเข้าถึงข้อมูลอุปกรณ์ไม่ได้จนกว่าผู้ดูแลจะกำหนดสิทธิ์
- รูปอุปกรณ์โหลดผ่าน Firebase Storage ด้วยบัญชีที่เข้าสู่ระบบ ไม่ใช้ลิงก์ดาวน์โหลดถาวร

ตัวอย่างการตั้งค่าเอเจนต์บน PowerShell:

เอเจนต์ต้องใช้ Node.js 22 ขึ้นไป

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS = "C:\Users\Martkung\.config\kusk-network-manager\agent-credentials.json"
cd agent
npm start
```

## Agent heartbeat และข้อมูลเก่า

- Agent ส่งสัญญาณทุก 1 นาทีไปยัง `monitoring/networkAgent` ด้วยเวลาจากเซิร์ฟเวอร์ Firebase
- หน้า Home, Switches และรายละเอียดอุปกรณ์แสดงสถานะ Agent และเวลาตรวจครบล่าสุด
- ไม่ได้รับ heartbeat เกิน 3 นาทีจะแสดงคำเตือน Agent อาจหยุดหรือขาดการเชื่อมต่อ
- ไม่ตรวจอุปกรณ์ครบเกิน 15 นาที หรือมีข้อผิดพลาด/ข้อมูลไม่ครบ จะแสดงคำเตือนผลตรวจเก่า
- สถานะรายอุปกรณ์ที่เกิน 15 นาทีหรือไม่มีเวลาตรวจจะแสดงเป็นสีเทาพร้อมคำว่า "ข้อมูลเก่า"
- การเพิ่มอุปกรณ์ใหม่จะรอเวลาตรวจจาก Agent การแก้ชื่อ/สถานที่ไม่ทำให้เวลาตรวจใหม่ขึ้น และการเปลี่ยน IP หรือสถานะด้วยมือจะล้างเวลาตรวจจนกว่า Agent ตรวจใหม่
- หน้าเว็บคำนวณอายุข้อมูลทุก 30 วินาที แม้ไม่มีข้อมูลใหม่ส่งมาจาก Firebase
- การขาดการเชื่อมต่อของเบราว์เซอร์จะแจ้งว่ายังยืนยันข้อมูลไม่ได้
- ผู้เยี่ยมชมเห็นคำเตือนจาก `lastSeen` ในชุดข้อมูลสาธารณะเดิม ไม่อ่านข้อมูล heartbeat ภายใน
- ผู้ดูและบัญชีที่มีสิทธิ์สูงกว่าอ่าน heartbeat ได้ แต่ทุกบัญชีในหน้าเว็บเขียนหรือปลอม heartbeat ไม่ได้
- ค่า `lastSuccessfulCheckAt` เปลี่ยนเฉพาะเมื่ออ่านข้อมูลและตรวจอุปกรณ์ครบทุกรายการสำเร็จ อุปกรณ์ Offline ที่ Ping ได้ตามปกติถือว่าตรวจสำเร็จ

ต้อง Deploy กฎและหน้าเว็บ พร้อมเริ่ม Agent รุ่นนี้ใหม่บนเครื่องที่เข้าถึงเครือข่ายภายในโรงเรียนได้:

```powershell
firebase deploy --only firestore:rules,hosting
cd agent
npm test
npm start
```

อย่าเปิด Agent หลายตัวพร้อมกัน ข้อมูล heartbeat ใช้สำหรับ Agent หลักหนึ่งตัว หากยังไม่ได้เริ่มรุ่นใหม่นี้ หน้าเว็บจะแสดงว่ายังไม่พบสัญญาณแทนการยืนยันว่าระบบปกติ การตั้งให้ Agent เริ่มอัตโนมัติควรทำบนเครื่องที่กำหนดให้ทำงานประจำและเก็บกุญแจไว้นอกโปรเจกต์

สำหรับเครื่อง Windows ประจำ ใช้คำสั่งนี้หลังตั้งค่า `GOOGLE_APPLICATION_CREDENTIALS` เพื่อเริ่มทันทีและเริ่มอีกครั้งหลังบัญชีนี้เข้าสู่ Windows:

```powershell
powershell -NoProfile -File agent/install-startup-task.ps1 -StartNow
```

Task Scheduler ใช้ชื่อ `KUSK Network Agent` ทำงานด้วยสิทธิ์ผู้ใช้ปกติ เริ่มใหม่ได้สูงสุด 3 ครั้งเมื่อโปรแกรมหยุดผิดปกติ และไม่เปิดซ้อนตัวเอง บันทึกการทำงานอยู่ใน `agent/logs/agent.log` ซึ่งไม่รวมใน Git งานนี้ต้องมีผู้ใช้เข้าสู่ Windows และเครื่องต้องไม่ Sleep; หากต้องการทำงานตั้งแต่บูตโดยไม่มีผู้ใช้เข้าสู่ระบบ ต้องตั้งค่าเครื่องบริการแยกต่างหาก

## ประวัติสถานะและแจ้งเตือน Offline

- เปิดหน้า `pages/monitoring.html` จากเมนู "สถานะและแจ้งเตือน" เพื่อดูเหตุการณ์และประวัติแยกตามอุปกรณ์
- Agent บันทึกครั้งแรกที่ตรวจพบ และบันทึกเพิ่มเฉพาะเมื่อสถานะเปลี่ยน ไม่สร้างประวัติซ้ำทุกครั้งที่ Ping
- เปิดเหตุการณ์เมื่อ Offline อย่างน้อย 3 รอบต่อเนื่อง และผ่านไปอย่างน้อย 10 นาทีจากรอบแรก
- เหตุการณ์เดิมไม่ถูกเปิดซ้ำหลังเริ่ม Agent ใหม่; เมื่อกลับมา Online จะปิดเป็น `resolved` อัตโนมัติ
- การตรวจผิดพลาด การเปลี่ยน IP และช่องว่างระหว่างการตรวจเกิน 15 นาทีจะเริ่มนับรอบที่ยังไม่ยืนยันใหม่
- ระยะเวลา Offline คำนวณถึงเวลาตรวจจริงล่าสุด ไม่เพิ่มเวลาที่ Agent หยุดเป็นเวลาขัดข้องที่ยืนยันแล้ว
- หากเหตุการณ์มีการขาดช่วงของผลตรวจ จะแสดง "มีช่วงขาดข้อมูล" ระยะเวลาที่แสดงคือช่วงระหว่างผลตรวจ มิใช่การยืนยันว่า Offline ทุกวินาทีในช่วงนั้น
- ผู้ดูอ่านประวัติและเหตุการณ์ได้ ผู้แก้ไข/ผู้ดูแลกดรับทราบได้โดยใช้เวลาของ Firebase และ UID ของตนเอง
- การรับทราบไม่ทำให้อุปกรณ์ Online และไม่ปิดเหตุการณ์ ผลตรวจและประวัติยังเขียนได้เฉพาะ Agent
- ข้อมูลใน `statusHistory` และ `networkIncidents` ไม่มี IP, MAC, Serial หรือ URL ตั้งค่า และไม่เปิดให้ผู้เยี่ยมชม
- `monitoringState` เป็นข้อมูลภายในของ Agent หน้าเว็บทุกสิทธิ์อ่านหรือเขียนไม่ได้
- หากลบอุปกรณ์หรือเปลี่ยน IP ระหว่างมีเหตุการณ์ จะปิดด้วยสาเหตุนั้นโดยไม่รายงานว่ากลับมา Online
- ประวัติเริ่มจากผลตรวจหลังใช้ Agent รุ่นนี้ ไม่สร้างประวัติย้อนหลังจากสถานะล่าสุดเดิม
- ช่องทางแจ้งเตือนที่ใช้งานได้ในชุดนี้คือรายการในเว็บ ตัวเลขบนเมนู และข้อความแจ้งเตือนบนหน้าที่แสดง heartbeat

ทดสอบการเปลี่ยนสถานะจริงในพื้นที่ Firebase แยกจากอุปกรณ์โรงเรียน (ไม่มีการ Ping หรือส่งข้อความภายนอก) และเผยแพร่กฎ/ดัชนี/หน้าเว็บ:

```powershell
cd agent
npm test
npm run security:verify-status
cd ..
firebase deploy --only firestore,hosting
```

หลัง Deploy ต้องเริ่ม Task `KUSK Network Agent` ใหม่เพื่อใช้โค้ดล่าสุด และรอให้ดัชนี Firestore สร้างเสร็จก่อนใช้ตัวกรองประวัติ ดัชนีทั้งหมดกำหนดไว้ใน `firestore.indexes.json`

## ประวัติการแก้ไขและถังขยะ

- เมนู "ประวัติข้อมูลและถังขยะ" (`pages/device-records.html`) แสดงผู้ดำเนินการ เวลา เหตุผล และค่าก่อน/หลัง โดยกรองตามอุปกรณ์ได้
- ผู้แก้ไข ผู้ดูแล และผู้ดูแลหลักอ่านประวัติและถังขยะได้ ข้อมูลนี้มี IP/MAC/Serial จึงไม่เปิดให้ผู้ดู บัญชีค่าเริ่มต้น หรือผู้เยี่ยมชม
- เพิ่ม/แก้ไขข้อมูล เปลี่ยนรูป ย้ายเข้าถังขยะ และกู้คืน ต้องบันทึก `deviceAudit` ในรายการเดียวกับข้อมูลจริง หากประวัติไม่ครบหรือไม่ตรงกัน ฐานข้อมูลปฏิเสธทั้งรายการ
- กฎตรวจ UID และอีเมลจากบัญชีที่ลงชื่อเข้าใช้ และใช้เวลาของ Firebase ไม่รับชื่อผู้ดำเนินการหรือเวลาที่ผู้ใช้ปลอมขึ้น
- ประวัติแก้ไข/ลบไม่ได้ผ่านหน้าเว็บทุกสิทธิ์ การป้องกันนี้ไม่ครอบคลุมผู้ถือสิทธิ์ Admin SDK/IAM ซึ่งต้องควบคุมแยกต่างหาก
- การลบต้องระบุเหตุผล และย้ายข้อมูลทั่วไป ข้อมูลภายใน และการอ้างอิงรูปไปเก็บใน `deviceTrash` โดยลบสำเนาจากรายการใช้งานและข้อมูลสาธารณะพร้อมกัน
- เฉพาะผู้ดูแลและผู้ดูแลหลักกู้คืนได้ ใช้รหัสอุปกรณ์เดิมและข้อมูลเดิม ไม่เขียนทับรหัสที่ใช้งานอยู่ หน้าเว็บตรวจ IP/MAC/Serial ที่ซ้ำก่อนกู้คืนด้วย แต่ไม่ได้เปลี่ยนนโยบายการอนุญาต IP ซ้ำของระบบเดิมเป็น unique constraint
- การกู้คืนเริ่มสถานะ `offline` และไม่มีเวลาตรวจจนกว่า Agent ตรวจจริงรอบใหม่ ผล Ping ที่เริ่มก่อนกู้คืนจะถูกปฏิเสธ และเหตุการณ์เก่าจะไม่ถูกรวมกับรอบชีวิตใหม่
- รูปต้นฉบับไม่ถูกลบหรือเขียนทับจากหน้าเว็บ การเอารูปออกเป็นการยกเลิกการอ้างอิงพร้อมบันทึกประวัติ ผู้ดูอ่านรูปของอุปกรณ์ในถังขยะไม่ได้
- ไม่มีปุ่มลบถาวรหรือการล้างถังขยะอัตโนมัติ ข้อมูลและรูปจะคงอยู่จนกว่าจะกำหนดนโยบายเก็บรักษา/ล้างข้อมูลฝั่งผู้ดูแลเพิ่มเติม ซึ่งมีผลต่อพื้นที่จัดเก็บ
- เริ่มเก็บประวัติจากการเปลี่ยนแปลงหลังเผยแพร่รุ่นนี้ ไม่สามารถกู้คืนอุปกรณ์หรือรูปที่ถูกลบถาวรก่อนหน้านี้ได้ การตรวจ Ping ปกติไม่สร้างประวัติการแก้ไขข้อมูล

ใช้ [Firebase Emulator Suite](https://firebase.google.com/docs/firestore/security/test-rules-emulator) ทดสอบการเปลี่ยนแปลงและทุกระดับสิทธิ์โดยไม่แตะข้อมูลจริง ต้องมี Firebase CLI และ Java 21 ขึ้นไป:

```powershell
npm --prefix agent test
firebase emulators:exec --only firestore,storage --project demo-network-audit --config firebase.test.json "npm --prefix agent run test:security"
```

กฎใช้ `getAfter()` ตรวจว่าข้อมูลกับประวัติอยู่ใน transaction เดียวกันตาม [แนวทางของ Firebase](https://firebase.google.com/docs/firestore/manage-data/transactions#data_validation_for_atomic_operations) ต้องเผยแพร่หน้าเว็บ กฎ Firestore/Storage และดัชนีพร้อมกัน และเริ่ม Agent ใหม่เพื่อใช้การแยกข้อมูลหลังการกู้คืน:

```powershell
firebase deploy --only firestore,storage,hosting
```

## ขั้นตอนปรับระบบเดิมให้ปลอดภัย

1. ยกเลิก Service Account Key เดิมใน Google Cloud IAM และสร้างกุญแจใหม่
2. เก็บกุญแจใหม่ไว้นอกโฟลเดอร์โปรเจกต์ แล้วตั้งค่า `GOOGLE_APPLICATION_CREDENTIALS`
3. ลบ Username และ Password เดิมออกจากข้อมูลอุปกรณ์ด้วยคำสั่งด้านล่าง
4. Deploy กฎความปลอดภัยและ Hosting ชุดใหม่

```powershell
cd agent
npm run security:remove-credentials
npm run security:sync-users
npm run security:migrate-private-data
npm run security:sync-public-switches
npm run security:configure-storage-cors
npm run security:verify-roles
cd ..
firebase deploy --only firestore,storage,hosting
```

การ Deploy กฎ Storage ครั้งแรกที่มีการอ่านสิทธิ์จาก Firestore ต้องทำในเทอร์มินัลแบบโต้ตอบ และยืนยันให้ Firebase CLI เพิ่มบทบาท `roles/firebaserules.firestoreServiceAgent` แก่ Firebase Storage service agent เมื่อระบบถาม

ต้องล้างข้อมูลรหัสผ่านเดิมก่อน Deploy หน้าเว็บชุดใหม่ เนื่องจาก Firestore ไม่สามารถซ่อนข้อมูลเป็นรายช่องได้ กฎใหม่จะป้องกันไม่ให้มีการเขียนช่อง `username` หรือ `password` กลับเข้าไปอีก

คำสั่ง `security:sync-users` จะนำบัญชีจาก Firebase Authentication มาสร้างหรืออัปเดตในคอลเลกชัน `users` โดยไม่เขียนทับสิทธิ์ที่กำหนดไว้แล้ว บัญชีผู้ดูแลหลักจะถูกยืนยันเป็น `owner` ทุกครั้ง

การเปิด `/login.html` โดยไม่มี `?signin=1` จะเข้าสู่หน้าผู้เยี่ยมชมโดยอัตโนมัติ ผู้ใช้ที่ต้องการเข้าสู่ระบบให้ใช้ `/login.html?signin=1` ระบบจะอ่านข้อมูลสาธารณะจากคอลเลกชันแยก `publicSwitches` เท่านั้น

## Encrypted Backups

คู่มือสำรองข้อมูลเข้ารหัสและทดสอบกู้คืนอยู่ใน [agent/BACKUP.md](agent/BACKUP.md)
สำรองวันที่ 1 ของทุกเดือน เวลา 02:00 น. ต้องมีบัญชี Windows นี้ลงชื่อเข้าใช้ เครื่องไม่ Sleep และเข้าถึง NAS ได้
ต้องตั้งรหัสป้องกันไฟล์กุญแจกู้คืนให้เสร็จก่อน จึงจะกู้คืนได้แม้สูญเสียเครื่องนี้
